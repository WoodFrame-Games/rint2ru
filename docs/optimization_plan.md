# План максимальной оптимизации поискового ядра

Отправная точка (2 vCPU, замеры из проекта):

| Ядро | Скорость |
|---|---|
| Словарный поиск (хэш-пробы, C++) | 14-15 млн цифр/сек |
| Словарный поиск (33к слов) | 6 млн цифр/сек |
| Целевой поиск (rolling u64, C++) | 409 млн цифр/сек |
| Целевой поиск (asm rs2) | ~874 млн цифр/сек |

## 1. Где узкое место

Словарный поиск: **~13 хэш-проб на цифру** (76 позиций × 13 длин = ~1000 проб на
окно). Каждая проба = перемешивание + обращение каблице (L2/L3 миссы).
Генерация цифр: ~6 циклов на цифру (mul-магия mod 10).
Целевой поиск: узкое место — только генерация цифр.

## 2. Алгоритмический уровень (наибольший выигрыш)

### 2.1 Автомат Ахо-Корасика (dict-поиск)
Один проход по ленте, O(1) на символ: состояние автомата обновляется на каждую
цифру, слова-кодопоследовательности выдаются на каждой терминальной позиции.
Пробы исчезают целиком. Ожидание: словарный поиск с 14 млн → **300-800 млн
цифр/сек** (упрётся в генерацию).

- Таблица переходов: узел = массив из 10 int32-индексов (40 узлов×10 = ~1.6 МБ
  для 40k слов — влезает в L2/L3);
- суффиксные ссылки — для слов, являющихся продолжением других;
- вывод: при переходе узел содержит битовую маску «здесь кончается слово
  длины ln» — есть ln в valid_len.

### 2.2 Bloom-фильтр перед хэшем (промежуточный вариант, проще AC)
Bitmap 2^18 бит (32 КБ, L1/L2): h = mix(code); если бит не установлен — кода
точно нет, проба не нужна. Отсекает ~99%+ отрицательных проб. Плюс ~×2-3 к
текущей скорости при минимуме кода. Можно сделать Фазой 1, AC — Фазой 2.

### 2.3 Идеальный хэш (MPHF)
Для фиксированного словаря можно построить perfect hash: ровно один доступ
вместо цепочки линейных проб. Ещё +10-30% поверх существующего.

### 2.4 DP вместо жадного выбора (качество, не скорость)
Максимальное непересекающееся покрытие интервалами — классическая задача:
жадный «самый длинный от старта» заменяется на DP по позициям (макс слов или
макс покрытие). Цена — микро-секунды на раунд.

## 3. Генерация цифр (второй узкой горлышко)

### 3.1 SIMD-конверсия (антисимметричный itoa)
Классический приём ( аналог Lemire «fast itoa»): 64-битный random → 19
десятичных цифр за несколько SIMD-инструкций (mul 10000000000000000000,
раскладка байтов по парам,表格 две цифры за байт). Ожидание: ~1-1.5 цикла
на цифру вместо ~6 → только это даёт х4 к целевому поиску.

### 3.2 AES-NI как RNG
AESENC — готовый «белый ящик» перемешиватель 128 бит за 4 цикла latency с
полным throughput. Counter-based: state128 += 1 → AESENC → 128 качественных
бит (~0.15-0.25 цикла/бит). Даёт ещё и детерминируемость (вопрос 41 отчёта:
seed = начальный counter). На Zen4/Xeon с AES-NI это быстрее xorshift64*.

### 3.3 N независимых лент в одном регистре (SIMD-параллелизм)
8 xorshift-состояний упакованы в регистр YMM (по 32 бита на ленту) — сдвиги и
XOR по 8 лентам одной инструкцией; деление на 10 через SIMD-mul (AVX2 mulhi
таблица). Итог: один цикл даёт 8 потоков цифр. С honestly-добавлением 2
виртуальных лент на поток получаем ×8-16 к генерации.

## 4. SIMD-сканирование словаря

### 4.1 N лент через AC-автомат
8 лент в uint8-состояниях упаковываются в регистр; переход: сначала
«байтовый» язык — таблица переходов хранится как [узел][цифра] → для 8 лент
нужен gather — на практике быстрее: для каждого узла хранить 10 узлов
успеха, тогда переход = table[узел*10 + цифра]; для 8 лент — movzx при
avx-vpgatherdd. AVX2 gather медленный (~12-20 тактов), выигрыш зависит от
пропорции кэш-миссов основного пути. Резерв: SSE-вариант с 4-мя лентами без
gather (перестановками pblendvb).

### 4.2 Простое SIMD: несколько лент через ручную развёртку
Более простой и предсказуемый путь: каждая итерация обрабатывает 4-8
независимых лент скалярно (ILP), состояния в регистрах. Компилятор разложит
на uops без задержек. Резерв +×2-3.

## 5. «Hex-уровень»: что реально даст ручнаяasm-оптимизация

Прямое письмо хексом = тот же ассемблер, только вручную — выигрыша формата
нет. Реальный прирост даёт работа НА УРОВНЕ микроархитектуры:

- branchless: CMOV вместо ветвлений в горячем цикле (предсказатель не сбивается);
- выравнивание цикла по 16/32 байта, NOP-паддинг;
- отсутствие зависимостей по цепочке (loop-carried deps): contradicts digit
  generation — разворачивается SIMD-ом;
- полное использование регистров (mov из памяти исключён — уже сделано в rs2);
- контроль uops: инструкция за инструкцией по таблицам uops.info;
- дизассемблирование результата компилятора (objdump) и ручное
  переписывание горячих участков в .asm — эталонный процесс «максимума».

Реалистичный прирост от ручной asm-подгонки поверх замеренно-оптимального
C++: ×1.2-1.8 (компилятор уже хорош; ручной asм полезен там, где он
сознательно плохо разворачивает).

## 6. Компиляторные экстра

```
-march=native -mtune=native   # все инструкции целевой машины
-flto -fprofile-generate/-fprofile-use   # PGO: +10-25%
-funroll-loops                   # развёртка горячего контура
static + to-file                 # без PLT-оверов
```

## 7. Аппаратный потолок и его математика

На 2 vCPU (одна SMT-пара ~3 ГГц):

- целевой поиск: генерация = узкое место → ~4 млрд цифр/сек (потолок ×10 к 409M);
- словарный (AC + SIMD-генерация): ~0.5-1.5 млрд цифр/сек (потолок ×35-100 к 14M).

Что меняется для целей:

| Цель | Сейчас | Потолок 2 vCPU |
|---|---|---|
| привет (10 цифр) | 48 сек | ~3-5 сек |
| приветдруг (16 цифр) | 283 суток | ~25-35 суток |
| 13-значные фразы | ~9 дней | ~30-40 часов |
| 14-значные | ~3.9 мес | ~12-14 дней |

## 8. Агрегация машин

Два vCPU-сервера = ×1.5-2 суммарно (линейно). Кластер из N машин — суммируется.
GPU (одна 4090): ~×1000 против CPU — но у нас vCPU-only. FPGA — потолок выше,
но разработка несоизмерима с экспериментом.

## 9. План фаз (исполнение по готовности)

- **Фаза 1** (простая): Bloom-фильтр + PGO/-march=native + remainder-фиксы.
  Ожидание ×2-3 (словарь 14 → 35-50 млн).
- **Фаза 2** (средняя): AC-автомат + SIMD-генерация цифр (AVX2 itoa).
  Ожидание ×10-30 словарному (50 → 300-800 млн). Также обновить ru4_target.
- **Фаза 3**: 8-lane SIMD-лент + ручной asm горячего цикла (уровень rs2,
  но для AC). Ожидание ещё ×2-4.
- **Фаза 4**: воспроизводимый counter-AES-RNG (детерминированная БЦ, вопрос 41).
- **Фаза 5** (необязательно): DP-выбор фраз, морфология — качество, не скорость.

## 10. Риски

- AC-таблица 1.6 МБ может вылезти из L2 при RR-вытеснении → мерить, в случае
  чего резать словарь до 8k самых частотных (уже 9000);
- SIMD-генерация модуля 10 даёт лёгкий скош в распределении (пренебрежимо);
- ручной asm: риск ошибок регресса — всегда держать C++-версию как референс
  для сверок (мы уже так делали с u64str).
